# ppb-server

uv + FastAPI + SQLAlchemy + SQLite + Alembic 기반 PPB 계정별 자원 서버입니다.
규칙 엔진은 **프로세스 내부의 Python 코드**입니다. 구매·개봉·판매·교환·도감·보상·
오리파 처리에 Swift 실행 파일이나 macOS 런타임을 사용하지 않습니다. 기존 확률·
천장·판형·가격 정책은 공개 정적 데이터와 고정 시드 비교 테스트로 보존합니다.

맥북 상시 실행, Cloudflare Tunnel, 고정 규칙 데이터와 계정 이전 운영 절차는
[macOS 배포 안내](docs/macos-deployment.md)를 따릅니다.

## 시작하기

```bash
uv sync --locked
cp .env.example .env
bash scripts/run-local.sh
```

`PPB_RULES_BACKEND=python`, `PPB_RULES_DATA_DIRECTORY=./data`가 기본 구성입니다.
`data/`에는 검증된 공개 규칙·카탈로그·시세만 있으며 이미지·개인 세이브는 없습니다.
Swift는 개발 시 데이터 재추출과 결과 비교에만 사용합니다. 규칙 갱신 시
`scripts/export-native-data.py`로 새 공개 데이터를 생성하고
`scripts/verify-native-rules.py`로 일치 여부를 확인하세요.
Swift 장애 폴백은 없으며 `PPB_RULES_BACKEND=swift`는 명시적 롤백/비교용입니다.
바이너리, DB, 개인 세이브와 `.env`는 커밋하지 않습니다. 기본 바인딩은 localhost 전용입니다.

- API 문서: <http://127.0.0.1:8000/docs>
- 상태 확인: <http://127.0.0.1:8000/health>
- DB 마이그레이션과 실제 규칙 실행 확인: <http://127.0.0.1:8000/ready>

## 앱 연결 / 다중 기기

수정된 앱 설정의 **온라인 계정 · 이메일 로그인**에서 서버 주소를 입력하고
`새 계정 가입`으로 이메일과 비밀번호를 등록합니다. 비밀번호는 8~128자입니다.
가입/로그인하면 온라인 모드가 저장됩니다. 앱을 완전히 재시작하세요.
다른 기기에 같은 서버 주소와 이메일·비밀번호로 로그인하면 같은 계정을 사용합니다.
기기 ID는 설치마다 별도로 생성되므로 복사하지 마세요.

이메일은 로그인 ID이며 **이메일 수신 인증은 하지 않습니다**. Google/OAuth 설정은
필요하지 않습니다. 기존 UUID 서버 계정은 아래 일회용 연결 코드로 가입 시 연결합니다.

기존 로컬 세이브는 자동 업로드/병합/삭제하지 않습니다. 온라인 캐시를 따로
저장하고, 온라인 모드를 끈 뒤 재시작하면 원래 로컬 세이브로 돌아갑니다.
토큰 수집은 연결 후 각 기기의 기준선부터 따로 누적하며 과거 사용량을 소급 지급하지 않습니다.

다른 Mac의 localhost는 서버 Mac이 아닙니다. 다음과 같이 SSH 터널을 연결하거나
사설 HTTPS 엔드포인트를 사용하세요. 앱은 원격 HTTP 평문 연결을 거부합니다.

```bash
# 다른 Mac에서 실행하고 앱에는 http://127.0.0.1:8000 입력
ssh -N -L 8000:127.0.0.1:8000 user@server-mac
```

## 신뢰 경계

- 계정 UUID만으로 접근할 수 없습니다. 모든 게임 API는 유효한 로그인 세션과
  해당 세션의 기기 ID가 필요합니다. 계정은 서버가 세션으로 결정합니다.
- 비밀번호는 Argon2id(19 MiB, 반복 2, 병렬도 1)로 해시합니다.
  서버에는 세션 토큰의 SHA-256 해시만, 앱에는 세션 토큰만 Keychain에 보관합니다.
  비밀번호를 앱 설정이나 로그에 저장하지 않습니다.
- 세션은 7일간 유효합니다. 같은 기기 재로그인은 이전 세션을 폐기하고,
  비밀번호 변경/운영자 재설정은 모든 세션을 폐기합니다.
- 인증 시도는 이메일당 분당 10회, IP당 분당 30회로 제한합니다. SQLite에 기록되어
  서버 재시작/다중 worker에서도 공유됩니다. 기본 실행은 전달 IP 헤더를 신뢰하지 않습니다.
- 원격 배포는 사설망/VPN, TLS, 접근 제한을 별도 구성해야 합니다.
  선택적 `PPB_GATEWAY_KEY`는 서버와 앱 실행 환경에 동일하게 설정합니다.
  이 공유 키가 계정별 로그인/권한을 대신하지는 않습니다.
- 요청대로 토큰 수집 방식/실사용량은 검증하지 않습니다. 기기별 보고 누적값의
  최고점을 넘은 증가분만 적립하고 도감 보너스는 서버의 Python 규칙으로 계산합니다.
  조작된 보고나 같은 사용량 원천이 여러 기기에서 중복 집계되는 것은 탐지하지 않습니다.
- 서버가 가격·잔액·추첨·천장·판형·쿠폰·판매·보상을 결정합니다.
  클라이언트 가격, 시드, 추첨 결과, 전체 상태 덮어쓰기 HTTP API는 없습니다.
- 오리파의 경품 목록은 공개하지만 실제 미개봉 봉투/카드 대응은 숨깁니다.

## API 계약

모든 `/v1/*` 요청에 `Authorization: Bearer <access_token>`과 UUID 형식의
`X-PPB-Device-ID` 헤더가 필요합니다. `X-PPB-Account-ID`는 선택적 일치 검사이며,
다른 계정을 지정하면 403입니다. 공유 키를 설정했다면 `X-PPB-Gateway-Key`도 필요합니다.

| 인증 API | 용도 |
| --- | --- |
| `POST /auth/register` | 이메일·비밀번호·device_id로 가입, 선택적 link_code |
| `POST /auth/login` | 이메일·비밀번호·device_id로 로그인 |
| `GET /auth/me` | 현재 계정/이메일/기기 |
| `POST /auth/logout` | 현재 세션 폐기 |
| `POST /auth/logout-all` | 해당 계정의 모든 세션 폐기 |
| `POST /auth/change-password` | current_password/new_password, 변경 후 전체 로그아웃 |

가입/로그인 응답은 `access_token`, `token_type`, `expires_at`(Unix 초),
`account_id`, `device_id`, `email`입니다. 인증된 API는 Bearer와 기기 헤더를 사용합니다.
비밀번호·세션·연결 코드를 URL, 셸 이력, 이슈, 로그에 남기지 마세요.

| API | 용도 |
| --- | --- |
| `GET /v1/state` | 최신 상태, 잔액, revision |
| `GET /v1/rules` | 규칙·카탈로그·도감 버전 (시세와 분리) |
| `POST /v1/commands` | 자원 변경, 결과와 최신 상태 반환 |
| `GET /v1/events?after=0&limit=50` | 계정별 명령/결과/잔액 로그; 최대 200건 |

```json
{
  "request_id": "9ad51a56-05dc-40ee-a22e-fc9031debb53",
  "expected_revision": 0,
  "command": {"kind": "report_tokens", "collected_total": 50000}
}
```

지원 명령: `initialize`, `report_tokens`, `report_bonus`, `buy_packs`, `open_packs`,
`sell_spares`, `sell_bulk`, `claim_dex`, `claim_gift`, `pull_oripa`, `refresh_oripa`,
`set_preferences`. 세부 필드는 `/docs`에 있습니다. 앱은 `rules_version`도 보내
규칙이 다르면 변경을 거절합니다. 가격 관련 요청은 별도 `price_version`과
`quoted_tokens`도 검사합니다. 보너스 창 인스턴스는 해시해 보내며
공급자 인증 토큰은 보내지 않습니다.

## 재시도 / 대량 작업 / 장애

- 일관된 읽기 스냅샷에서 규칙을 계산한 뒤 짧은 `BEGIN IMMEDIATE` 구간에서
  계정 revision·원본 상태·세션·기기/적립 정책·시세·예약 카드를 다시 확인합니다.
  다른 요청이 먼저 변경했으면 409로 거절하며, 상태·이벤트·작업 진행은 함께 확정합니다.
- 오래된 `expected_revision`은 409로 거절하고 취소합니다. 앱에서 동기화 후
  사용자가 다시 요청합니다. 변경된 가격으로 임의 재구매하지 않습니다.
- 같은 계정의 동일 ID/기기/본문은 원래 결과와 **현재** 상태를 반환합니다.
  개봉을 다시 추첨하지 않습니다.
- 통신 장애/503은 **새 ID를 만들지 말고 동일 요청 그대로 재시도**하세요.
  앱은 전송 전에 요청을 디스크에 보관하고 재시작 때 복구합니다.
  복구된 개봉은 알림과 개봉 이력/도감에서 확인할 수 있습니다.
- 401/세션 만료에도 미확인 요청은 보존합니다. 같은 계정으로 재로그인하면 같은
  요청 ID로 복구하며 다시 추첨하지 않습니다. 미확인 요청이 있으면 계정 전환을 막습니다.
- 요청당 구매·개봉·단일 판매는 1,000개, 일괄 판매는 1,000종입니다.
  앱은 더 큰 수량을 나누어 처리합니다. **전체 묶음이 한 트랜잭션은 아닙니다.**
  중간 중단 시 확정된 부분은 남고 미확인 요청은 복구합니다.
- 오프라인에서 로컬 자원을 대신 사용하지 않습니다. 캐시 열람만 가능합니다.
- SQLite의 최종 쓰기는 직렬화되지만 무거운 게임 계산은 다른 계정의 쓰기를 막지 않습니다.
  대규모 공개 마켓용 다중 DB 구성은 아닙니다.
- 앱은 약 10초마다 상태 버전을 확인합니다. ETag가 같으면 304로 응답하여
  카드 전체를 매번 전송하거나 캐시 세이브를 다시 쓰지 않습니다.
- 온라인에서는 개인 시세 덮어쓰기를 사용하지 않습니다. 서버가 발행한 카드/팩
  스냅샷을 계정별 온라인 캐시에 저장합니다. 시세 갱신은 앱 재설치가 필요 없지만,
  규칙·카탈로그·도감 변경은 서버 데이터와 클라이언트의 규칙 버전을 함께 맞춰야 합니다.
  이번 Python 전환은 규칙 버전과 API를 보존하므로 기존 v0.11.12 앱과 호환됩니다.

## 자동 운영 온라인 기능

### 계정 관리와 운영 안전장치 (0006)

- 메뉴바 설정은 **일반 / 표시 / 데이터 / 고급**으로 나눈다. 일반의 ‘계정 및 서버…’는
  별도 창을 열며 **연결 / 보안 / 기기 / 서버 상태**를 제공한다. 온라인 창에서도 열 수 있다.
  기존 세이브 이전, 공급자 스캔, 로그, 업데이트, 개봉 설정은 제거하지 않았다.
- `/auth/devices`: 자신의 활성 로그인 기기만 조회한다. 기기 이름 변경과 개별 세션 폐기를
  지원한다. 최근 로그인 시각은 온라인 접속 상태가 아니며, 해제한 기기도 다시 로그인할 수 있다.
- `/auth/recovery`: 현재 비밀번호 재확인 후 256비트 난수 복구 코드를 한 번 표시한다.
  서버는 해시만 저장한다. 재발급/비밀번호 변경/운영자 재설정으로 기존 코드는 무효화된다.
  오프라인 보관용으로 시간 만료는 없고 한 번만 사용할 수 있다. 잃어버리면 재발급한다.
- `/auth/recover`: 이메일·복구 코드·새 비밀번호로 복구하고 모든 세션을 폐기한다.
  자동 로그인하지 않는다. 원문은 앱/로그에 보관하지 않으며, 모르는 계정과 틀린 코드는
  같은 오류로 응답한다. 메일 수신 인증·발송·MFA를 제공한다는 뜻은 아니다.
- 복구 코드 발급 응답이 유실되면 비밀번호로 명시적으로 재발급한다. 복구 완료 응답이
  유실됐다면 새 비밀번호로 먼저 로그인한다. 자원 변경의 미확인 요청은 삭제하지 않는다.
- `/auth/token-policy`: 기본은 기존 기기별 사용량 합산이다. 비밀번호를 확인하고 현재
  로그인한 기기만 적립하도록 선택할 수 있다. 정책 버전 충돌은 409이다.
  전환 후 각 기기의 첫 보고는 기준값만 저장하고 이후 증가분부터 적립한다.
  비담당 기기의 보고도 누적 최고점을 갱신하되 지급하지 않는다. 기존 잔액은 바꾸지 않는다.
  이는 동일 사용량을 여러 기기가 읽는 상황의 운영상 예방책이지 공급자 사용량 진위 검증이 아니다.
- 서버가 켜져 있으면 첫 실행과 이후 24시간마다 SQLite backup API로 백업한다.
  무결성·외래 키 검사와 별도 임시 DB 복원 검사가 성공한 파일만 발행한다.
  `PPB_BACKUP_DIRECTORY`(기본 `.data/backups`), `PPB_BACKUP_KEEP`(기본 14개)로 설정한다.
  성공 후에만 자체 파일명의 오래된 백업을 정리하고 수동 백업·다른 파일은 건드리지 않는다.
  실패하면 기존 백업을 보존하고 1시간 후 재시도한다. 서버 디스크 고장 대비는 별도 외부 백업이 필요하다.
- `/v1/server/status`: 로그인한 사용자에게 백업·시세·거래 만료 작업의 성공/실패/지연을
  표시한다. 파일 경로·다른 계정 정보는 노출하지 않는다. 온라인 창은 보이는 동안만
  갱신하고 실패/지연을 안내한다. DB 쓰기 대기·규칙 처리의 최근 200회 P50/P95는
  프로세스별 진단값이며 재시작 시 초기화된다.
- 상태 조회에서 만료 대상이 없으면 쓰기 잠금을 잡지 않는다. 시세는 DB별 최근 4개
  버전의 JSON·응답 문자열을 캐시하고, Python 가격표·세트 가격·오리파 후보도 재사용한다.
  변경 없는 인벤토리는 projection 일치만 확인하며, 누락·불일치는 복구한다.
  진단 지표는 준비·순수 계산·쓰기 잠금 대기·쓰기 트랜잭션 시간을 구분한다.
- 1,000팩 초과 개봉은 `/v1/opening-jobs`에 진행 기록을 만든다. 각 1,000팩 묶음의
  지급·이력·통계·진행 수량은 같은 트랜잭션에서 확정된다. 동일 요청 재전송은 같은 결과다.
  온라인 창 **작업**에서 다른 기기로도 이어가기/일시정지/남은 작업 취소가 가능하다.
  창 또는 앱을 닫으면 진행 중 묶음까지만 처리하며 서버가 혼자 다음 팩을 열지 않는다.
  팩을 예약하지 않으므로 다른 기기에서 소비하거나 개봉 모드가 바뀌면 이어하기를 거절한다.
  큰 구매·판매의 서버 작업화는 이번 개봉 작업 기능에 포함되지 않는다.

구현 기준: [SQLite Online Backup API](https://www.sqlite.org/backup.html),
[OWASP 오프라인 계정 복구 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#offline-methods).
실서비스 DB로 자동 복원하지 않는다. 복구는 운영자가 서버를 중지하고 전체 DB를 함께 복원한다.

메뉴바의 **온라인 · 통계와 거래** 또는 온라인 설정의 버튼으로 별도 창을 엽니다.
작은 팝오버의 크기와 개봉 흐름은 그대로이며 온라인 창은 740×540 이상으로 조절됩니다.
창을 닫거나 최소화하면 온라인 목록의 15초 폴링을 멈춥니다. 기본 게임 동기화는 계속됩니다.

### 시세와 통계

- TCGCSV의 일일 데이터 발행 이후 **UTC 21:00 (한국 06:00)**에 갱신합니다.
  서버 시작 시 놓친 작업을 수행하고 실패하면 마지막 정상 시세를 유지해 1시간 후 재시도합니다.
- 네트워크 수집은 쓰기 잠금 밖에서 수행합니다. 카드와 팩을 한 불변 스냅샷으로 검증한 뒤
  활성 버전만 원자적으로 바꿉니다. 작업 실행권은 DB에 저장하여 여러 worker의 중복 실행을 막습니다.
- 기존 등록 카드/세트만 갱신하며 애매한 매칭과 누락은 기존 값·항목별 날짜를 보존합니다.
  실거래 기반 추정 참고가와 TCGplayer 시장가를 구분합니다. 새 세트나 홀로 규칙을 만들지 않습니다.
- `GET /v1/prices`, `/v1/prices/snapshot`: 현재 버전·마지막 성공·실패·다음 실행과 스냅샷.
  `POST /v1/quotes`: 구매/분해/오리파의 서버 견적. 확인 금액·버전이 달라지면 409입니다.
  이미 확정된 요청은 새 시세여도 이전 결과를 재전송합니다.
- `GET /v1/stats?days=7&mode=realistic&set_id=sv8pt5`: 0/7/30일, 모드, 세트 필터.
  구매·개봉·지출·분해수입·희귀도·판형·팩 변형·신규/중복 획득량과 비율, 현재 평가액.
  개봉 관측률은 보장 확률이 아닙니다. 최근 1,000팩 로컬 이력과 무관하게 이벤트를 집계합니다.
  과거 이벤트가 없는 구매원가/개봉은 추정하지 않고 기록 시작일을 표시합니다.

### 친구와 전시

- `/v1/profile`: 닉네임, 재발급 가능한 친구 코드와 공개 범위. 로그인 UUID·이메일 검색은 없습니다.
- `/v1/friends`: 요청/수락/거절/삭제/차단. 요청은 7일 후 만료합니다.
  승인된 친구여도 컬렉션·위시리스트·바인더 각각 기본 비공개입니다.
- `/v1/wishlist`: 카드 + 선택적 판형 + 목표 수량(최대 500개 항목).
  `/v1/binder`: 계정당 1개, 최대 36칸, 보유 판형을 지정하고 순서 변경.
- `/v1/inventory`, `/v1/matches`: 판형별 보유·예약·거래 가능량과 상호 교환 후보.
  추천은 양쪽이 위시리스트 공개를 켠 승인 친구에게만 제공하며 자동 체결하지 않습니다.
- `/v1/notifications`: 커서 기반 앱 내 알림과 읽음 처리. 이메일/OS 푸시는 없습니다.
  조회 권한은 서버에서 검사하며 잔액·사용량·상세 개봉 이력은 공유하지 않습니다.

### 교환과 마켓

- `/v1/trades`: 친구끼리 카드 대 카드. 한쪽당 최대 20판형/1,000장, 72시간 만료.
  제안자 카드를 즉시 예약하고 수락 시 상대 수량·상태를 검증해 양쪽을 한 트랜잭션으로 이전합니다.
  수정은 취소 후 재등록입니다. 친구 삭제·차단은 미완료 교환을 취소합니다.
- `/v1/market/listings`: 같은 서버의 로그인 사용자에게 공개되는 고정가/무수수료 마켓.
  등록당 최대 1,000장, 장당 1~10^12 정수 토큰. 부분 구매 가능, 남은 수량은 7일 후 해제.
  가격 변경은 취소 후 재등록합니다. 자기 거래와 차단 관계의 신규 거래는 거절합니다.
- 동일 카드·동일 판형을 한 장 남긴 **중복분만** 거래합니다. 예약한 카드는 소유권과
  도감·바인더에 남지만 기존 전체 분해 판매를 포함한 다른 감소 경로에서 사용할 수 없습니다.
- 모든 변경은 `request_id`, `expected_revision`을 요구하고 기존 교환/판매 글 변경에는
  `target_id`, `target_version`도 필요합니다. 구매는 확인한 `unit_tokens`, `quantity`를 보냅니다.
  동시 구매로 수량이 부족해도 임의 부분 결제하지 않습니다. 서버가 원자적으로 카드·재화·예약·
  양쪽 버전·로그·알림·재시도 영수증을 확정합니다. 마켓 수입/지출은 별도 누적 장부입니다.
- 만료는 분 단위 내부 작업과 요청 시 검사합니다. 중단 중 지난 만료는 재시작 후 처리합니다.
  `PPB_JOBS_ENABLED=0`은 격리된 테스트용으로만 사용하세요. 일상 운영은 관리자가 이벤트를
  등록할 필요가 없지만 서버가 꺼지면 다른 기기 접속과 자동 작업도 중단됩니다.
- 토큰 수집을 신뢰하는 사설 경제입니다. 부정 적립 방지, 현금 가치, 공개 서비스용 경제 보안을
  보장하지 않습니다. 경매·구매 주문·채팅·현금 결제·경쟁 순위·시즌 운영은 없습니다.

### 업데이트, 대조와 복구

업데이트 전 미확인 요청을 복구하고 서버를 중지한 뒤 다음 순서를 따릅니다.
기존 백업/규칙 경로를 덮어쓰지 마세요. 마이그레이션 0004는 시세/통계, 0005는 온라인 거래입니다.

```bash
uv run --env-file .env python -m app.admin backup .data/before-online-UNIQUE.sqlite3
uv run --env-file .env alembic upgrade head
uv run --env-file .env python -m app.admin reconcile
# 이상이 없을 때 조회 테이블/누락 통계만 정본에서 재구축
uv run --env-file .env python -m app.admin reconcile --apply
```

`reconcile`은 Swift 정규화를 사용하고 예약량이 보유량을 넘으면 중단합니다.
개인 세이브를 자동 이전하지 않습니다. DB에는 상태·거래·예약·영수증·시세·작업 실행권이
모두 들어 있어 SQLite backup API로 함께 백업합니다. 복구 시 서버를 완전히 중지하고
현재 DB와 WAL/SHM을 별도로 보존한 후 백업 DB를 복사해 해당 버전의 앱/규칙으로 시작하세요.
확정된 거래 이후의 오래된 백업으로 복원하면 그 이후 거래가 사라집니다. 두 계정을 개별 복원하지 마세요.
실패 시 온라인 창의 시세 오류와 `server_jobs.error`, `/ready`, 자원 이벤트를 먼저 확인합니다.
로그인 정보나 원본 HTTP 본문을 진단 로그에 추가하지 마세요.

## 기존 세이브 가져오기 (운영자 명시 실행)

앱을 종료하고 원본 세이브와 DB를 먼저 백업하세요. HTTP 업로드는 없습니다.
**사용한 적 없는 새 UUID**로만 가져올 수 있으며 기존 계정 덮어쓰기/병합은 거절합니다.
입력은 원본 `game-state.json`이며 내보내기 봉투 형식은 지원하지 않습니다.

```bash
uv run --env-file .env python -m app.admin backup /absolute/path/ppb-backup.sqlite3
# 기본은 검사만 수행 (dry-run)
uv run --env-file .env python -m app.admin import-save --account NEW_UUID --file /path/game-state.json --source-format legacy-local-v1
# 검사 후에만 --apply 추가
uv run --env-file .env python -m app.admin import-save --account NEW_UUID --file /path/game-state.json --source-format legacy-local-v1 --apply
# 기존/가져온 UUID 계정에 이메일 로그인을 연결: 출력된 코드를 앱 가입 화면에 입력
uv run --env-file .env python -m app.admin issue-link-code --account EXISTING_UUID
```

연결 코드는 10분간 한 번만 유효하며 새로 발급하면 이전 코드는 무효화됩니다.
가입 시 기존 잔액·카드·revision·기기별 적립 기록은 그대로 유지합니다.
UUID 또는 이메일만으로 기존 계정을 가져오거나 자동 병합하지 않습니다.

`legacy-local-v1` 가져오기는 보너스 지급 ID를 온라인 SHA-256 형식으로 한 번 변환하고
원본/정규화 파일 해시를 기록합니다. 동일 세이브를 다른 UUID로 다시 가져올 수 없으며,
정규화가 카드·팩·재화·보상 이력을 잃으면 저장 전에 중단합니다. 온라인 캐시는 입력하지 마세요.
새 사용자는 앱에서 이메일과 비밀번호만으로 가입합니다. 초대 코드는 필요 없습니다.
운영자가 계정을 미리 만들어 줄 때만 `python -m app.admin create-invite`로 코드를 발급하고,
사용자는 가입 화면의 연결 코드 칸에 넣습니다.

비밀번호를 잊었을 때는 미리 발급해 보관한 복구 코드로 앱에서 재설정할 수 있습니다.
복구 코드가 없다면 서버 운영자가 아래 명령으로 재설정합니다. 비밀번호는
숨김 입력으로 두 번 받으며 모든 세션을 폐기합니다. 메일 발송/이메일 복구는 없습니다.

```bash
uv run --env-file .env python -m app.admin reset-password --email player@example.com
```

백업은 SQLite backup API로 확정된 WAL까지 포함하며 기존 파일을 덮어쓰지 않습니다.
복원은 서버를 중지하고 백업을 **새 경로**에 복사한 뒤 `PPB_DATABASE_URL`을
그 경로로 변경합니다. 현재 DB는 보존하세요.

## 로그 / 운영

`game_events`에 계정·기기·요청·명령·결과·규칙 버전·잔액 전후·시간을
자원 변경과 같은 트랜잭션으로 저장합니다. HTTP 상태/소요 시간은 JSON으로
stderr에 기록하며 헤더, UUID, 본문, 쿼리는 운영 로그에 남기지 않습니다.
`auth_events`에는 가입·로그인·로그아웃·재설정·제한 발생을 기록하며 비밀번호,
이메일, 세션/연결 코드 원문은 넣지 않습니다. DB의 이메일은 개인 정보이므로 백업도 보호하세요.
기본 실행 스크립트는 `umask 077`을 적용합니다.

개봉 결과와 재시도 기록 때문에 DB가 계속 커집니다. 일일 자동 백업 외에 별도 디스크의
백업과 운영 로그 수집/회전을 구성하세요. 이벤트를 단순 삭제하면 과거 요청이 다시
실행될 수 있으므로 장기 보관 축소에는 별도의 중복 방지 기록 설계가 필요합니다.
